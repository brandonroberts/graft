# Graft spec — draft v1

> **Status: draft.** This spec describes what the reference implementation (`@graftsync/spec`,
> `@graftsync/core`, `@graftsync/adapter-patch`) does today. It stays a draft, and may change
> without a version bump, until a second, unrelated mechanism has been implemented against it
> ([#6](https://github.com/brandonroberts/graft/issues/6)). Only then is v1 frozen.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. Where this document
says MUST, the reference tooling enforces it (by an error diagnostic, a refusal, or a failing
exit code) unless noted otherwise.

## 1. The `.grafts/` directory

A project opts into Graft by having a `.grafts/` directory at its root. Tools find the
project root by walking up from the working directory to the nearest directory that contains
`.grafts/`.

```
.grafts/
  config.json              # optional project configuration (§7)
  <graft-id>/              # one directory per graft
    graft.md               # the intent file (§2), REQUIRED
    variants/              # variant modules, by convention (paths are listed in graft.md)
    ...                    # anything else the graft needs (oracle scripts, fixtures)
  .cache/                  # tool-owned: pristine upstream contents and registry cache (gitignored)
  .report/                 # tool-owned: sync reports (gitignored) (§6)
  .vendor/                 # patch mechanism, vendor applier: patched tarballs (committed)
  .patch-package/          # patch mechanism, patch-package applier: derived patches (committed)
  .shared/                 # convention: files shared between grafts (e.g. oracle helpers)
```

- Every **non-hidden** subdirectory of `.grafts/` that contains a `graft.md` is a graft.
  Subdirectories without a `graft.md` are ignored.
- Directories whose name starts with `.` are **never** loaded as grafts. They are reserved
  for tooling (`.cache/`, `.report/`, `.vendor/`, `.patch-package/`) and for project
  conventions such as `.shared/`. Grafts MAY reference files in `.shared/` (for example
  `import … from '../.shared/oracle.mjs'` in an oracle).
- Grafts are loaded in sorted directory-name order. A graft that fails validation is reported
  as invalid; it is never silently dropped.
- `.cache/` and `.report/` are regenerated by tools and SHOULD be gitignored (`graft init`
  writes a `.grafts/.gitignore` that does this). `.vendor/` and `.patch-package/` hold derived
  files that the package manager installs from, so they MUST be committed when their applier
  is in use, and MUST NOT be edited by hand.

## 2. `graft.md`

`graft.md` is a Markdown file that MUST start with YAML frontmatter delimited by `---` lines
(a leading BOM is ignored). Missing or unclosed frontmatter, or frontmatter that isn't valid
YAML, is an error.

### 2.1 Frontmatter

| Field | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `id` | string matching `^[a-z0-9][a-z0-9-]*$` | yes | — | Graft id (lowercase kebab-case). MUST equal the graft's directory name. |
| `rootstock` | object | yes | — | The upstream package. |
| `rootstock.package` | non-empty string | yes | — | npm package name of the upstream. |
| `rootstock.verified` | semver version | yes | — | Last upstream version the oracle passed against. |
| `mechanism` | non-empty string | yes | — | Name of the mechanism adapter that applies the graft (e.g. `patch`). MUST name an adapter the tooling has registered. |
| `targets` | array of non-empty strings | no | — | Upstream files the mechanism operates on, relative to the package root. |
| `variants` | array of variant objects, at least one | yes | — | One mechanism implementation per upstream version range. |
| `variants[].range` | semver range | yes | — | Upstream versions this variant is valid for. Validated with `includePrerelease`. |
| `variants[].module` | non-empty string | yes | — | Path of the variant module, relative to the graft directory. |
| `oracle` | object | yes | — | The command that proves the invariants hold (§5). |
| `oracle.command` | non-empty string | yes | — | Shell command; exit 0 means pass. |
| `oracle.modes` | array of non-empty strings, at least one | no | `["default"]` | Modes to run the oracle in (e.g. `dev`, `build`). |
| `oracle.timeout` | positive integer (seconds) | no | 600 (applied by the runner) | Per-mode timeout. |
| `status` | `applied` \| `conflicted` \| `upstreamed` \| `obsolete` | no | `applied` | Lifecycle state (§4). |

Unknown frontmatter keys are ignored. Tools that edit `graft.md` (bookkeeping such as
`verified`, `status`, `variants` and History) MUST preserve YAML comments, formatting and the
body.

### 2.2 Body sections

The body MUST contain these level-2 (`## `) sections. Headings are matched
case-insensitively; headings inside fenced code blocks don't count. The recommended order is
the order below.

| Section | Content |
|---|---|
| `## Why` | What the modification enables and why upstream doesn't do it. |
| `## Invariants` | Observable behaviors that must hold. This is the contract the oracle tests. |
| `## Where to look` | The upstream area involved, described by behavior rather than file path. |
| `## Anchors` | What each variant matches on, and why that anchor was chosen. |
| `## History` | Dated entries recording what changed upstream and how the graft adapted. |

A **missing** section is an error. An **empty** section is a warning. Other sections are
allowed.

## 3. Validation

A graft is valid when it has no error diagnostics. Diagnostics, by code:

| Code | Severity | Rule |
|---|---|---|
| `frontmatter/missing` | error | No `---`-delimited frontmatter. |
| `frontmatter/yaml` | error | Frontmatter is not valid YAML. |
| `frontmatter/invalid` | error | Frontmatter fails the schema in §2.1. |
| `frontmatter/id-mismatch` | error | `id` differs from the directory name. |
| `frontmatter/unknown-mechanism` | error | No registered adapter has the `mechanism` name. |
| `body/missing-section` | error | A required section is absent. |
| `body/empty-section` | warning | A required section has no content. |
| `variants/overlap` | error | Two variant ranges intersect (with `includePrerelease: true`). Every version MUST select at most one variant. |
| `variants/duplicate-module` | error | The same `module` path is listed by more than one variant. |
| `variants/verified-uncovered` | warning | `rootstock.verified` is not satisfied by any variant range. |

## 4. Variants and status

### 4.1 Variant selection

For an upstream version `V`, the selected variant is the **first** entry of `variants` whose
`range` is satisfied by `V`, with prereleases included (`includePrerelease: true`). Because
ranges MUST NOT overlap, at most one variant matches. When none matches, the graft has no
variant for `V`; `sync` reports that as `needs-agent`.

**The `-0` floor convention.** A range that should also cover the prereleases of its first
version SHOULD start at that version's `-0` prerelease: `>=5.0.0-0` selects `5.0.0-rc.1` as
well as `5.0.0`. Upper bounds follow the same convention: `<5.0.0-0` excludes the 5.0.0
prereleases.

### 4.2 Adding variants

Existing variant modules MUST NOT be edited. A change for a new upstream range is a new
module, registered with a new `variants` entry. When registering (`record_variant` in MCP,
`recordVariant` in core), the tooling:

- refuses a range that isn't a valid semver range, a module outside the graft directory, a
  module that doesn't exist, and a module that's already registered;
- **narrows** each existing variant whose range overlaps the new one by capping it below the
  new range's minimum version: each `||` alternative of the old range gets `<min` appended
  (`>=4.0.0` becomes `>=4.0.0 <5.0.0-0` for a new range `>=5.0.0-0`). If narrowing is
  disabled, the capped range would be empty, or it would still overlap, the registration is
  refused;
- calls the adapter's `validateVariant`, if any;
- appends a History entry;
- when asked to verify at a version, checks anchors there and rolls `graft.md` back if any
  miss.

### 4.3 Status

| Status | Active | Meaning |
|---|---|---|
| `applied` | yes | The graft is applied and verified at `rootstock.verified`. |
| `conflicted` | yes | The graft can't currently be made to satisfy its invariants; a human must decide. |
| `upstreamed` | no | Upstream now provides the behavior; the graft is retired. |
| `obsolete` | no | The graft is no longer needed. |

Tooling applies and verifies only **active** grafts (`applied`, `conflicted`). `sync` reports
inactive grafts as `skipped`. `rootstock.verified` MUST only be set to a version the oracle
has passed against.

## 5. The oracle contract

The oracle is the only proof that a graft holds. Anchors matching, or a clean apply, is not
success.

- `oracle.command` is run **once per mode**, in the order of `oracle.modes`, through a shell,
  with the **project root** (the directory containing `.grafts/`) as working directory.
- Every occurrence of `{mode}` in the command is replaced by the mode name.
- The process inherits the caller's environment, plus:

  | Variable | Value |
  |---|---|
  | `GRAFT_ID` | The graft id. |
  | `GRAFT_DIR` | Absolute path of the graft directory. |
  | `GRAFT_MODE` | The current mode. |
  | `GRAFT_PACKAGE` | `rootstock.package`. |
  | `GRAFT_UPSTREAM_VERSION` | The upstream version under test (by default the installed version; empty if not installed). |

- A mode **passes** when the command exits 0 before the timeout (`oracle.timeout` seconds,
  default 600). On timeout the process receives `SIGTERM` and the mode fails. A command that
  fails to start fails.
- The oracle **passes** only when at least one mode ran and every mode passed.
- An oracle SHOULD fail without the graft applied, and SHOULD test every invariant plus at
  least one pre-existing behavior the graft must not break. An oracle MUST NOT be weakened to
  make a sync pass.

## 6. Sync

`sync` is the deterministic first pass. For each active graft (optionally filtered by id or
package), grouped by `rootstock.package`, with target version `T` (the given version, else
the installed version):

1. **Static checks, before anything is installed**, against the pristine published contents
   of `T`: select the variant (§4.1), check its anchors, and apply it into
   `.grafts/.report/<id>/applied/`. Any failure marks the graft `needs-agent`.
2. **Install.** If `T` isn't installed and every graft on the package passed step 1, install
   `T` (only when installing was requested; otherwise the grafts get `error`). The adapter's
   `beforeInstall` runs first and `afterInstall` after. If some grafts on the package need an
   agent, nothing is installed and the passing ones are `skipped`.
3. **Oracle,** against the installed `T`, in every mode. Failure marks the graft
   `needs-agent`. On success, unless it's a dry run, `rootstock.verified` becomes `T`,
   `status` becomes `applied`, and a History entry is appended.

When a graft is marked `needs-agent` and `T` differs from `rootstock.verified`, a scoped
upstream diff from `verified` to `T` is written to `.grafts/.report/<id>/diff.patch` (and
`diff.json`).

Outcomes per graft: `green`, `needs-agent`, `skipped`, `error`. Invalid grafts are always
reported as `error`.

**Exit codes:**

| Code | Meaning |
|---|---|
| `0` | All grafts green (or skipped). |
| `1` | One or more grafts need an agent, and none errored. |
| `2` | Tooling error: an invalid graft, a failed install, an uninstalled target without `--install`, or another error. Takes precedence over `1`. |

**Report files:** `.grafts/.report/sync.json` (the full machine-readable report) and
`.grafts/.report/sync.md` (a human/agent summary with reasons, missed anchors, failing oracle
output and the diff path).

## 7. `.grafts/config.json`

Optional. MUST be valid JSON if present. All keys are optional.

| Key | Type | Meaning |
|---|---|---|
| `upstream` | `{ [package]: string }` | Spec template used instead of the npm registry to fetch and install the package. `{version}` is substituted; relative `file:` paths resolve against `.grafts/`. Example: `{ "lib": "file:../mirror/lib-{version}" }`. |
| `resolveFrom` | `{ [package]: string }` | Directory, relative to the project root, whose `node_modules` resolution determines the installed version (for monorepos where a workspace package declares the dependency). Example: `{ "pacote": "packages/core" }`. |
| `mechanisms` | `{ [mechanism]: object }` | Mechanism-specific options. |
| `mechanisms.patch.applier` | `pnpm` \| `npm` \| `bun` \| `graft` \| `patch-package` \| `vendor` | Forces the `patch` mechanism's applier instead of choosing one from the package manager. Any other value is an error. |

## 8. Package-manager detection

Starting at the project root and walking up, in each directory:

1. If `package.json` declares `packageManager` as `pnpm@…`, `npm@…`, `upm@…`, `yarn@…` or
   `bun@…`, that package manager wins.
2. Otherwise the first lockfile found, in this precedence order:
   1. pnpm: `pnpm-lock.yaml` or `pnpm-workspace.yaml`
   2. npm: `package-lock.json` or `npm-shrinkwrap.json`
   3. upm: `upm.lock`
   4. yarn: `yarn.lock`
   5. bun: `bun.lock` or `bun.lockb`

With no signal in any directory, the package manager is **npm**.

The `patch` mechanism's default applier follows from this: pnpm → `pnpm`; npm ≥ 12 → `npm`;
npm < 12 and yarn → `graft` (built-in postinstall applier); bun → `bun`; upm → `vendor`.

## 9. Mechanism adapters

A mechanism is implemented by a `MechanismAdapter` (exported by `@graftsync/core`), registered
under the name used in `mechanism`.

| Member | Required | Contract |
|---|---|---|
| `name` | yes | The mechanism name. |
| `apply(ctx, { version?, outDir? })` | yes | Apply the variant selected for `version` (default: installed) to the pristine upstream; write modified files under `outDir` when given. Report per-file results and `ok`. |
| `checkAnchors(ctx, version)` | yes | Report which anchors of the selected variant match or miss in the pristine upstream at `version`, with errors for a missing variant or target. |
| `scopeDiff(ctx, from, to)` | yes | Diff the upstream between two versions, narrowed to the regions the graft targets. |
| `beforeInstall?(ctx, version)` | no | Point the package manager at the variant for `version` before `sync` installs it. May return `{ install: 'reinstall' }` to request a bare reinstall instead of a targeted install. |
| `afterInstall?(ctx, version)` | no | Run right after `sync` installs `version`, for mechanisms that apply themselves. |
| `applyInstalled?(ctx)` | no | Apply selected variants to installed package copies (from `postinstall`). MUST be idempotent, work offline, and never modify files shared with a package-manager store (write new inodes). |
| `validateVariant?(ctx, variant)` | no | Validate a new variant before it is registered; throw to reject. |
| `variantExtension?` | no | File extension for scaffolded variant modules (default `.ts`). |
| `variantTemplate?(graft)` | no | Contents of a scaffolded variant stub. |

Every adapter MUST follow these rules:

1. **Fail loudly.** A missing or ambiguous anchor, a missing target, or a variant that doesn't
   apply is an error. A graft MUST NOT silently apply nothing.
2. **Anchor by behavior.** Anchors SHOULD use stable, behavior-level markers (exported
   symbols, public API, user-facing strings) rather than code shape, and MUST NOT depend on
   formatting.
3. **Add variants, never rewrite them.** Older version ranges keep their variants. Adapters
   MUST NOT modify existing variant modules.
4. **Diff what the mechanism sees.** Anchors, apply and diffs MUST operate on the published
   package contents (what the package manager installs), not upstream source repositories.
