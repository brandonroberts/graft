# Graft spec — draft v1

> **Status: draft, ready to freeze.** This spec describes what the reference implementation
> (`@graftsync/spec`, `@graftsync/core`, `@graftsync/adapter-patch`, `@graftsync/adapter-fork`,
> published as 0.1.x) does today. The freeze condition, a second, unrelated mechanism implemented
> against it, is met: `fork` (§9.2) uses the same adapter interface as `patch` (§9.1), with only
> optional hooks added. v1 is frozen once
> [#6](https://github.com/brandonroberts/graft/issues/6) closes; until then it may change
> without a version bump.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. Where this document
says MUST, the reference tooling enforces it (by an error diagnostic, a refusal, or a failing
exit code) unless noted otherwise.

## 1. The `.grafts/` directory

A project opts into Graft by having a `.grafts/` directory at its root. Tools find the
project root by walking up from the working directory to the nearest directory that contains
`.grafts/`.

```
.grafts/
  config.json              # optional project configuration (§7)
  <graft-id>/              # one directory per graft
    graft.md               # the intent file (§2), REQUIRED
    variants/              # variant modules, by convention (paths are listed in graft.md)
    ...                    # anything else the graft needs (fixtures, notes)
  .cache/                  # tool-owned: pristine upstream contents, registry cache, fork clones (gitignored)
  .report/                 # tool-owned: sync reports (gitignored) (§6)
  .vendor/                 # patch mechanism, vendor applier: patched tarballs (committed)
  .patch-package/          # patch mechanism, patch-package applier: derived patches (committed)
  .shared/                 # convention: files shared between grafts (e.g. test helpers)
```

- Every **non-hidden** subdirectory of `.grafts/` that contains a `graft.md` is a graft.
  Subdirectories without a `graft.md` are ignored.
- Directories whose name starts with `.` are **never** loaded as grafts. They are reserved
  for tooling (`.cache/`, `.report/`, `.vendor/`, `.patch-package/`) and for project
  conventions such as `.shared/`. Grafts MAY reference files in `.shared/` (for example
  `import … from '../.shared/check.mjs'` in a graft's test script).
- Grafts are loaded in sorted directory-name order. A graft that fails validation is reported
  as invalid; it is never silently dropped.
- `.cache/` and `.report/` are regenerated by tools and SHOULD be gitignored (`graft init`
  writes a `.grafts/.gitignore` that does this). `.vendor/` and `.patch-package/` hold derived
  files that the package manager installs from, so they MUST be committed when their applier
  is in use, and MUST NOT be edited by hand.

## 2. `graft.md`

`graft.md` is a Markdown file that MUST start with YAML frontmatter delimited by `---` lines
(a leading BOM is ignored). Missing or unclosed frontmatter, or frontmatter that isn't valid
YAML, is an error.

### 2.1 Frontmatter

| Field | Type | Required | Default | Meaning |
|---|---|---|---|---|
| `id` | string matching `^[a-z0-9][a-z0-9-]*$` | yes | — | Graft id (lowercase kebab-case). MUST equal the graft's directory name. |
| `rootstock` | object | yes | — | The upstream package. |
| `rootstock.package` | non-empty string | yes | — | Name of the upstream package in its ecosystem: an npm name, a crate name, a Go module path (a `/v2` major is a different module) or a PyPI project name. For a standalone graft (§9), any name for the upstream. |
| `rootstock.ecosystem` | `npm` \| `cargo` \| `go` \| `pypi` | no | `npm` | The package ecosystem (§10). Selects the version scheme (§4.1), where pristine upstream comes from, and the appliers. A standalone graft installs nothing, so its ecosystem only selects the version scheme. |
| `rootstock.verified` | version in the ecosystem's scheme (§4.1) | yes | — | Last upstream version the graft was verified against (§5). In fork repo mode it may name a commit as build metadata (`22.3.0-next.2+e36a63e20e`, §9.2). |
| `mechanism` | non-empty string | yes | — | Name of the mechanism adapter that applies the graft (e.g. `patch`). MUST name an adapter the tooling has registered. |
| `targets` | array of non-empty strings | no | — | Upstream files the mechanism operates on, relative to the package root. |
| `variants` | array of variant objects, at least one | yes | — | One mechanism implementation per upstream version range. |
| `variants[].range` | range in the ecosystem's scheme (§4.1) | yes | — | Upstream versions this variant is valid for, prereleases included. |
| `variants[].module` | non-empty string | yes | — | Path of the variant module, relative to the graft directory. |
| `generator` | object | no | — | A command that writes a new variant mechanically; `sync` runs it when no existing variant fits (§6). |
| `generator.command` | non-empty string containing `{out}` (or using `$GRAFT_VARIANT_OUT`) | yes, with `generator` | — | `{version}` and `{out}` are substituted. |
| `fork` | object | yes for `mechanism: fork` | — | Where a fork graft's modification lives (§9.2). |
| `fork.repo` | non-empty string | yes | — | Git URL of the fork, or a path relative to the project root (e.g. `.` when the graft lives in the fork). |
| `fork.upstream` | non-empty string | yes | — | Git URL of the upstream source repository. |
| `fork.tag` | string containing `{version}` | no | `v{version}` | Upstream release tag for a version. |
| `fork.install` | `package` \| `none` | no | `package` | `none`: repo mode — the fork is the product, nothing is installed (§9.2). |
| `fork.track` | non-empty string | no | — | Repo mode: an upstream branch whose tip `outdated` offers (`<version>+<commit>`). |
| `fork.dir` | non-empty string | no | repo root | Package directory inside the repositories (monorepos). |
| `fork.build` | non-empty string | no | — | Command run in the rebased package directory before packing. |
| `fork.timeout` | positive integer (seconds) | no | 1800 | Build timeout. |
| `status` | `applied` \| `conflicted` \| `upstreamed` \| `obsolete` | no | `applied` | Lifecycle state (§4). |

Unknown frontmatter keys are ignored. Tools that edit `graft.md` (bookkeeping such as
`verified`, `status`, `variants` and History) MUST preserve YAML comments, formatting and the
body.

### 2.2 Body sections

The body MUST contain these level-2 (`## `) sections. Headings are matched
case-insensitively; headings inside fenced code blocks don't count. The recommended order is
the order below.

| Section | Content |
|---|---|
| `## Why` | What the modification enables and why upstream doesn't do it. |
| `## Invariants` | Observable behaviors that must hold, and which of the project's tests cover them. The contract whoever changes the graft verifies (§5). |
| `## Where to look` | The upstream area involved, described by behavior rather than file path. |
| `## Anchors` | What each variant matches on, and why that anchor was chosen. |
| `## History` | Dated entries recording what changed upstream and how the graft adapted. |

A **missing** section is an error. An **empty** section is a warning. Other sections are
allowed.

## 3. Validation

A graft is valid when it has no error diagnostics. Diagnostics, by code:

| Code | Severity | Rule |
|---|---|---|
| `frontmatter/missing` | error | No `---`-delimited frontmatter. |
| `frontmatter/yaml` | error | Frontmatter is not valid YAML. |
| `frontmatter/invalid` | error | Frontmatter fails the schema in §2.1. |
| `frontmatter/id-mismatch` | error | `id` differs from the directory name. |
| `frontmatter/unknown-mechanism` | error | No registered adapter has the `mechanism` name. |
| `frontmatter/unknown-ecosystem` | error | `rootstock.ecosystem` is not one of the ecosystems in §10. |
| `body/missing-section` | error | A required section is absent. |
| `body/empty-section` | warning | A required section has no content. |
| `variants/overlap` | error | Two variant ranges intersect (prereleases included). Every version MUST select at most one variant. For PEP 440 the test may over-approximate (report an overlap no real version is in), never under-approximate. |
| `variants/duplicate-module` | error | The same `module` path is listed by more than one variant. |
| `variants/verified-uncovered` | warning | `rootstock.verified` is not satisfied by any variant range. |
| `frontmatter/fork-missing` | error | `mechanism: fork` without a `fork` block. |
| `frontmatter/oracle-ignored` | warning | An `oracle` block from an earlier draft; it is ignored (§5). |
| `graft/duplicate-rootstock` | error | Two active grafts with an `exclusivePerPackage` mechanism (§9) target the same package in the same ecosystem. Reported on both. |

## 4. Variants and status

### 4.1 Variant selection

Versions and ranges use the rootstock ecosystem's **version scheme**:

| Ecosystem | Scheme | `verified` | `range` |
|---|---|---|---|
| `npm`, `cargo` | semver | `4.2.0` | node-semver range (`>=4.0.0 <5.0.0`), not Cargo's caret-by-default requirement syntax |
| `go` | semver; the `v` prefix is optional | `v0.14.0`, pseudo-versions (`v0.0.0-20240101120000-abcdef123456`, a prerelease ordered by time), `v2.1.0+incompatible` | node-semver range |
| `pypi` | PEP 440 | `2.31.0`, `1.0.post1`, `2.0rc1`, `1!0.5` | PEP 440 specifier set (`>=2.0,<3`; `==2.*`, `~=2.31`, `!=`, `===`) |

PEP 440 matching follows the PEP as implemented by Python's `packaging` 26 (`<V` excludes V's
own prereleases unless V is one; `>V` excludes V's local and post-releases unless V is a
post-release), with prereleases included.

For an upstream version `V`, the selected variant is the **first** entry of `variants` whose
`range` is satisfied by `V`, with prereleases included. Because ranges MUST NOT overlap, at
most one variant matches. When none matches, the graft has no variant for `V`; `sync` reports
that as `needs-agent`.

**The floor convention.** A range that should also cover the prereleases of its first version
SHOULD start at that version's earliest prerelease: `>=5.0.0-0` in semver selects `5.0.0-rc.1`
as well as `5.0.0`, and `>=5.0.dev0` does the same in PEP 440. Upper bounds follow the same
convention: `<5.0.0-0` (or `<5.0.dev0`) excludes the 5.0.0 prereleases.

### 4.2 Adding variants

Existing variant modules MUST NOT be edited. A change for a new upstream range is a new
module, registered with a new `variants` entry. When registering (`graft variant add` in the CLI,
`recordVariant` in core), the tooling:

- refuses a range that isn't valid in the ecosystem's scheme, a module outside the graft
  directory, a module that doesn't exist, and a module that's already registered;
- **narrows** each existing variant whose range overlaps the new one by capping it below the
  new range's minimum version: in semver each `||` alternative of the old range gets `<min`
  appended (`>=4.0.0` becomes `>=4.0.0 <5.0.0-0` for a new range `>=5.0.0-0`); in PEP 440 the
  specifier set gets `,<min` (`>=4.0` becomes `>=4.0,<5.0.dev0` for `>=5.0.dev0`). If narrowing is
  disabled, the capped range would be empty, or it would still overlap, the registration is
  refused;
- calls the adapter's `validateVariant`, if any;
- appends a History entry;
- refuses a verify version outside the new range (it would check a different variant);
- when asked to verify at a version, checks anchors there and rolls `graft.md` back if any
  miss.

### 4.3 Status

| Status | Active | Meaning |
|---|---|---|
| `applied` | yes | The graft is applied and verified at `rootstock.verified`. |
| `conflicted` | yes | The graft can't currently be made to satisfy its invariants; a human must decide. |
| `upstreamed` | no | Upstream now provides the behavior; the graft is retired. |
| `obsolete` | no | The graft is no longer needed. |

Tooling applies and checks only **active** grafts (`applied`, `conflicted`). `sync` reports
inactive grafts as `skipped`. `rootstock.verified` MUST only be set to a version the graft was
verified against (§5).

## 5. Verification

Graft runs **no runtime check**. What the tooling proves is mechanical: that a graft's variant
still fits the target upstream (its anchors match, it applies), and, when asked, that the target
installs with it. Whether the modified software still *behaves* as the Invariants say is the job
of whoever changes the graft, usually an agent, with the project's own tests.

- `sync` records a graft green (§6) when the mechanical checks pass. A variant that applies
  unchanged to a new version is the cheap path: nothing about the change moved, so the project's
  normal CI is its behavioral check.
- When a graft needs an agent, the agent MUST verify every Invariant at the target version before
  recording it (`variant add --verify-version`, `sync`, `mark --verified`), with the project's
  tests. Where no test covers an Invariant, it SHOULD add one. Tests MUST NOT be weakened to make
  a graft pass, and a graft whose Invariants can't be met is marked `conflicted`.
- The `## Invariants` section SHOULD say which tests cover each Invariant (or how to check it), so
  the next agent can verify the same way.
- A frontmatter `oracle` block (from earlier drafts) is ignored, with the warning
  `frontmatter/oracle-ignored`.

## 6. Sync

`sync` is the deterministic first pass. For each active graft (optionally filtered by id, package or
ecosystem), grouped by `rootstock.package`, with target version `T` (the given version, else
the installed version). A standalone graft (§9) is a group of its own: its default `T` is
`rootstock.verified` (a re-verification), and it has no install step.

Grafts are grouped by `(rootstock.ecosystem, rootstock.package)`, so an npm `ms` and a crate
`ms` never share an install. Each result and target in the report carries its `ecosystem`.

1. **Static checks, before anything is installed**, against the pristine published contents
   of `T`: select the variant (§4.1), check its anchors, and apply it into
   `.grafts/.report/<id>/applied/`. Any failure marks the graft `needs-agent`.
2. **Install.** If `T` isn't installed and every graft on the package passed step 1, install
   `T` (only when installing was requested; otherwise the grafts get `error`). The adapter's
   `beforeInstall` runs first and `afterInstall` after. If some grafts on the package need an
   agent, nothing is installed and the passing ones are `skipped`.
3. **Record.** For a standalone graft, the adapter's `workspace` materializes the upstream at `T`
   with the graft applied (§9.2); if that fails, the graft needs an agent. Then, unless it's a dry
   run, `rootstock.verified` becomes `T`, `status` becomes `applied`, and a History entry is
   appended, in `graft.md`, or, when the adapter's `recordsInResult` says so, only in the
   materialized result (§9.2, in place). The adapter's `afterVerified` then runs. Sync checks
   fit, not behavior (§5).

**Generators.** A graft with a `generator` that fails step 1 gets one regeneration attempt: the
command runs from the project root with `GRAFT_ID`, `GRAFT_DIR`, `GRAFT_PACKAGE`,
`GRAFT_UPSTREAM_VERSION`, `GRAFT_VARIANT_OUT` and `GRAFT_EXIT_UPSTREAMED` set. If it exits 0 and
wrote the variant, the variant is registered and the graft re-checked; it is kept only if steps
1–3 then pass, and rolled back otherwise. If it exits with `GRAFT_EXIT_UPSTREAMED` (`3`), it is
saying upstream at `T` already does what the graft did (e.g. the package now ships the
modification itself): nothing is registered, and the graft is reported `needs-agent` and
*likely upstreamed*, for a human to confirm and set `status: upstreamed`. Any other exit is a
failure, reported with the command's error message.

When a graft is marked `needs-agent`, the adapter's `prepareAgent` (if any) prepares a starting
point, reported as the graft's `agentStart` ("Start from" in `sync.md`). When `T` also differs
from `rootstock.verified`, a scoped upstream diff from `verified` to `T` is written to
`.grafts/.report/<id>/diff.patch` (and `diff.json`).

A graft is reported *likely upstreamed* (`likelyUpstreamed`) when its adapter finds the target
already contains its change, or its generator says so. The outcome stays `needs-agent`: a human
confirms and sets `status: upstreamed`.

Outcomes per graft: `green`, `needs-agent`, `skipped`, `error`. Invalid grafts are always
reported as `error`.

**Exit codes:**

| Code | Meaning |
|---|---|
| `0` | All grafts green (or skipped). |
| `1` | One or more grafts need an agent, and none errored. |
| `2` | Tooling error: an invalid graft, a failed install, an uninstalled target without `--install`, or another error. Takes precedence over `1`. |

**Report files:** `.grafts/.report/sync.json` (the full machine-readable report) and
`.grafts/.report/sync.md` (a human/agent summary with reasons, missed anchors, the diff path
and the agent's starting point).

### 6.1 Finding new versions (`outdated`)

For each rootstock package (per ecosystem), the newest version above every graft's `verified`
among the dist-tags considered (default `latest`, `next`, `rc`, `beta`; prereleases included).
npm reports its registry's dist-tags; the other ecosystems report `latest` (the newest stable
version) and `next` (the newest prerelease, when it is newer), skipping yanked and retracted
versions. A
standalone graft has no dist-tags: its adapter's `newerVersion` supplies the candidate, one
entry per graft (`standalone: true`).

## 7. `.grafts/config.json`

Optional. MUST be valid JSON if present. All keys are optional.

| Key | Type | Meaning |
|---|---|---|
| `ecosystems` | `{ [ecosystem]: object }` | Ecosystem options (§10). `ecosystems.npm` takes `upstream` and `resolveFrom` (below), which win over the top-level keys. |
| `upstream` | `{ [package]: string }` | npm: spec template used instead of the npm registry to fetch and install the package. `{version}` is substituted; relative `file:` paths resolve against `.grafts/`. Example: `{ "lib": "file:../mirror/lib-{version}" }`. |
| `resolveFrom` | `{ [package]: string }` | npm: directory, relative to the project root, whose `node_modules` resolution determines the installed version (for monorepos where a workspace package declares the dependency). Example: `{ "semver": "packages/core" }`. |
| `mechanisms` | `{ [mechanism]: object }` | Mechanism-specific options. |
| `mechanisms.patch.applier` | string, or `{ [ecosystem]: string }` | Forces the `patch` mechanism's applier instead of choosing one from the ecosystem's tooling. A string names npm's applier (`pnpm` \| `npm` \| `bun` \| `yarn` \| `graft` \| `patch-package` \| `vendor`); the object form names one per ecosystem (§10). A name that isn't one of the ecosystem's appliers is an error. |

## 8. Package-manager detection (npm)

For npm grafts, starting at the project root and walking up, in each directory:

1. If `package.json` declares `packageManager` as `pnpm@…`, `npm@…`, `upm@…`, `yarn@…` or
   `bun@…`, that package manager wins.
2. Otherwise the first lockfile found, in this precedence order:
   1. pnpm: `pnpm-lock.yaml` or `pnpm-workspace.yaml`
   2. npm: `package-lock.json` or `npm-shrinkwrap.json`
   3. upm: `upm.lock`
   4. yarn: `yarn.lock`
   5. bun: `bun.lock` or `bun.lockb`

With no signal in any directory, the package manager is **npm**.

The `patch` mechanism's default applier follows from this: pnpm → `pnpm`; npm ≥ 12 → `npm`;
npm < 12 and yarn → `graft` (built-in postinstall applier); bun → `bun`; upm → `vendor`.

## 9. Mechanism adapters

A mechanism is implemented by a `MechanismAdapter` (exported by `@graftsync/core`), registered
under the name used in `mechanism`.

| Member | Required | Contract |
|---|---|---|
| `name` | yes | The mechanism name. |
| `apply(ctx, { version?, outDir? })` | yes | Apply the variant selected for `version` (default: installed) to the pristine upstream; write modified files under `outDir` when given. Report per-file results and `ok`. |
| `checkAnchors(ctx, version)` | yes | Report which anchors of the selected variant match or miss in the pristine upstream at `version`, with errors for a missing variant or target. |
| `scopeDiff(ctx, from, to)` | yes | Diff the upstream between two versions, narrowed to the regions the graft targets. |
| `beforeInstall?(ctx, version)` | no | Point the package manager at the variant for `version` before `sync` installs it. May return `{ install: 'reinstall' }` to request a bare reinstall instead of a targeted install. |
| `afterInstall?(ctx, version)` | no | Run right after `sync` installs `version`, for mechanisms that apply themselves. |
| `applyInstalled?(ctx)` | no | Apply selected variants to installed package copies (from `postinstall`). MUST be idempotent, work offline, and never modify files shared with a package-manager store (write new inodes). |
| `standalone?(graft)` | no | True when the graft installs nothing into the project. Its current version is `rootstock.verified`, `sync` skips the install step (and defaults to re-checking `verified`), and a green sync materializes `workspace` as its result. |
| `workspace?(ctx, version)` | with `standalone` | Materialize the upstream at `version` with the graft applied, as the graft's result (e.g. a branch to fetch); returns `{ dir, result?, fetch?, dispose }` (`result`/`fetch`: where to get the materialized result afterwards). Throw when it can't be done. |
| `afterVerified?(ctx, version, update?)` | no | Called by `sync` after a green result (not on dry runs); `update` is the graft.md change when `recordsInResult` said to record it in the result. |
| `recordsInResult?(ctx, version)` | no | True when a green sync at `version` is recorded in the materialized result instead of graft.md; `afterVerified` then receives the update. |
| `newerVersion?(ctx)` | no | For standalone grafts (no dist-tags): the newest upstream version above `verified`, with where it came from. `outdated` lists one entry per such graft (`standalone: true`). |
| `prepareAgent?(ctx, version)` | no | Called by `sync` when a graft needs an agent: prepare a starting point and return `{ description, repo?, ref?, upstream?, conflicts?, next? }` (`agentStart`; `description` is shown as "Start from", and `next`, when set, replaces the report's usual "write a new variant" next step). |
| `capture?(ctx, version)` | no | `graft capture`: the change made to the installed copy at `version`, as a variant module (the patch mechanism: the diff against the pristine package; what the installed copy is depends on the ecosystem, §10). Throw when there's nothing capturable (`capture/no-changes`), including an installed copy that is exactly pristine + the selected variant, which would only register a duplicate of it. The tooling replaces the selected variant only while it is still the scaffold stub, otherwise registers a new one (§4.2), and keeps it only if it applies to pristine `version`. |
| `validateVariant?(ctx, variant)` | no | Validate a new variant before it is registered; throw to reject. |
| `exclusivePerPackage?` | no | When true, at most one active graft with this mechanism may target a package; more is a validation error. |
| `variantExtension?` | no | File extension for scaffolded variant modules (default `.ts`). |
| `variantTemplate?(input)` | no | Contents of a scaffolded variant stub. `input` has the graft's id, package, targets, the project root, and mechanism-specific `options` from `graft add`. |
| `scaffoldFrontmatter?(input)` | no | Extra frontmatter for a scaffolded graft (e.g. the `fork:` block). |

Every adapter MUST follow these rules:

1. **Fail loudly.** A missing or ambiguous anchor, a missing target, or a variant that doesn't
   apply is an error. A graft MUST NOT silently apply nothing.
2. **Anchor by behavior.** Anchors SHOULD use stable, behavior-level markers (exported
   symbols, public API, user-facing strings) rather than code shape, and MUST NOT depend on
   formatting.
3. **Add variants, never rewrite them.** Older version ranges keep their variants. Adapters
   MUST NOT modify existing variant modules.
4. **Diff what the mechanism sees.** Anchors, apply and diffs MUST operate on the pristine
   upstream artifact the mechanism modifies, never on the installed copy (which the mechanism
   itself changes): the published package for `patch`, the upstream source at the release
   tag for `fork`.

### 9.1 The `patch` mechanism

A variant is a git-style patch with package-relative paths, applied to the published package.
Every hunk is an anchor (fuzz 0; position may shift), and a created file MUST NOT already exist
upstream. An *applier* makes the package manager apply it (pnpm, npm ≥ 12, bun and yarn 2+
natively; a built-in `postinstall` applier; patch-package; or a vendored tarball). Details: the
README's *Mechanisms* section.

### 9.2 The `fork` mechanism

The modification lives as commits on a fork of the upstream source repository (`fork.repo`),
on top of an upstream release tag.

Package mode (the default, `fork.install: package`) packs with npm and installs through npm
overrides, so it is for `rootstock.ecosystem: npm` only; any other ecosystem is refused with
`fork/ecosystem`. Repo mode installs nothing and works for any repository.

- A variant is a JSON file `{ "ref": "<fork branch, fork tag or commit>", "base": "<upstream
  version>" }` (repo mode also allows commits and the `@worktree` / `@verified` sentinels,
  below). The graft's change is the diff from `tag(base)` to `ref`, limited to `fork.dir`.
  A ref with no changes is an error. Fork grafts are `exclusivePerPackage`.
- Anchors are that diff's hunks, located in the upstream source at `tag(version)` (fuzz 0). The
  change is "likely upstreamed" when its reverse applies to the target tag.
- To install a version, the tooling rebases the change onto `tag(version)`, runs `fork.build`
  if set, packs the package with `npm pack --ignore-scripts`, and MUST verify that it packs as
  `rootstock.package@version`. It commits the result as `.grafts/.vendor/<pkg>-<version>.tgz`
  and points overrides and the root dependency at it. The tooling MUST NOT push to the fork.
- At the installed version, checks MUST verify the committed tarball equals a fresh build and
  that the installed files equal the tarball's (except `package.json`).
- When the change doesn't rebase onto a new tag, the graft needs an agent: rebase the fork
  branch onto the new tag in the fork, then register a new variant pointing at it.
- The diff excludes `.grafts/`. Binary files carry over only where upstream left them as they
  were at the base (otherwise the anchor `<file>#binary` misses); executable bits carry over.
- When a graft needs an agent, the tooling SHOULD prepare the branch `graft/<id>/<version>-agent`
  in the cache clone: git's three-way merge of the change onto the target (`merge-tree` with
  the fork's base as merge base), conflict markers left in place, and name the conflicted
  files in the report.
- A hunk whose change is the first or last line of the base file (no context on that side)
  MUST miss when upstream has since added lines right against it, as git's merge would
  conflict. The scoped diff for an agent is taken from the fork's base, not from `verified`.

**Repo mode** (`fork.install: none`). The fork is the product itself (a translated docs site,
a tool run from source), not a dependency:

- The graft is standalone (§9): nothing is packed or installed, and the installed-copy checks
  don't apply. `base` may also be any upstream commit, tag or branch, since such forks often
  sit on a commit between releases.
- A target version is resolved through `fork.tag`, unless it carries a commit as semver build
  metadata (`22.3.0-next.3+57905ca4e6`): it then names that upstream commit, and the version
  part is what variant ranges match. Commit targets are for repo mode only.
- `sync` rebases the change onto `tag(version)` in a fresh checkout.
  The result is committed as the local branch `graft/<id>/<version>` in the cache clone
  (`.grafts/.cache/fork/<id>`), for the user to fetch. The tooling MUST NOT push it. The
  result's parent is the upstream target commit, which the report names (`upstream` on the
  fetchable ref; likewise for the `-agent` branch).
- **Adopting a result** into the fork SHOULD record that upstream commit as a second parent: a
  merge whose tree is the result (`git merge --no-ff --no-commit -s ours <upstream>`, then the
  tree swap). A single-parent commit would leave upstream out of the fork's history, so a later
  merge from upstream would replay it. The reference Action does this.
- The cache clone fetches every object of `fork.repo` and `fork.upstream`. When either is a
  local partial clone (`remote.<name>.promisor` or `extensions.partialClone`), the tooling MUST
  refuse it with a reason naming the cause (`fork/partial-clone`), not git's "repository
  corruption" error. A shallow clone is fine.
- When the graft lives in the fork (`fork.repo` is the project's own checkout), a green
  result also carries the project's `.grafts/` (without `.cache`, `.report` and `.vendor`),
  including the just-recorded verification, so adopting the result keeps the graft files.
- **In place.** A variant may use `"ref": "@worktree"` (the project's checkout, uncommitted
  changes included, `.grafts/` excluded; the graft must live in the fork) and
  `"base": "@verified"` (the upstream at `rootstock.verified`). With `@verified`, a green sync
  MUST record the new verification only in the result (`recordsInResult`), never in the
  checkout, which still holds the fork at its old base. The `-agent` branch's graft.md is set
  to the target version (status `conflicted` while markers remain), so `sync` on it verifies
  the resolved branch in place. Its `agentStart.next` says so (resolve, re-sync, take the
  result, commit; keep the variant), and is the report's "Next" line. When the checkout is
  already merging the result's upstream commit (it adopted the `-agent` branch), the green
  result's adoption hint takes only its tree (`git read-tree`), since git refuses a second merge;
  that tree carries graft.md with the verification recorded.
- `fork.track` (a branch) makes `outdated` offer that branch's tip as `<version>+<commit>`
  (the version from its `package.json`, else the newest tag); otherwise it offers the newest
  release tag above `verified` (`newerVersion`).

## 10. Ecosystems

A rootstock belongs to one ecosystem (`rootstock.ecosystem`, default `npm`). The ecosystem
decides the version scheme (§4.1), where the **pristine** upstream comes from (what anchors,
apply and scoped diffs read, §9 rule 4), where the installed copy is, how a version is installed
(`sync --install`), and which `patch` appliers exist. Each ecosystem's options live under
`ecosystems.<name>` in `.grafts/config.json` (§7).

Every applier MUST check that the ecosystem's tool actually uses the patched package, not just
that the configuration names it: each ecosystem below has a configuration that its tool accepts
with exit code 0 while silently installing the unpatched package, and `graft check` MUST fail on
it.

### 10.1 npm

- **Pristine:** `npm pack <pkg>@<version>`, run from the project root so its `.npmrc` applies,
  or `ecosystems.npm.upstream` (alias `upstream`).
- **Versions:** `npm view <pkg> versions dist-tags`.
- **Installed copy:** `node_modules/<pkg>` walking up from the project root (or
  `ecosystems.npm.resolveFrom`), or through Plug'n'Play.
- **Install and appliers:** §8 and §9.1.

### 10.2 cargo

- **Pristine:** the published `.crate`, fetched by cargo itself: a throwaway package under
  `.grafts/.cache` that depends on `<crate> = "=<version>"` is `cargo fetch`ed (so the project's
  `.cargo/config.toml` registries, mirrors and auth apply), and the `.crate` is extracted from
  cargo's registry cache, never from the shared, editable `registry/src` copy. Its `Cargo.toml`
  is the one `cargo publish` normalized (the author's file is `Cargo.toml.orig`); variants patch
  the published files.
- **Versions:** the registry's sparse index (`ecosystems.cargo.index`, default
  `https://index.crates.io`); yanked versions are skipped.
- **Installed copy:** `cargo metadata` for `ecosystems.cargo.manifest` (default `Cargo.toml`):
  the copy from a path source (the vendored crate) if there is one, else the newest.
- **Install:** `cargo update -p <crate>@<installed> --precise <version>`; reinstall:
  `cargo fetch`.
- **Applier `cargo-vendor` (the default and only one):** pristine + variant is written to
  `.grafts/.vendor/<crate>-<version>/` (committed), and the workspace root manifest (from
  `cargo locate-project --workspace`) gets
  `[patch.<registry>] <crate> = { path = ".grafts/.vendor/<crate>-<version>" }` (`registry`
  from `ecosystems.cargo.registry`, default `crates-io`). The edit keeps the file's comments
  and formatting, and refuses a `[patch]` written as dotted keys or an inline table. Other
  versions' vendored directories are removed.
- **Silent failure:** a `[patch]` whose version doesn't match what the requirements resolve is
  not used, yet cargo exits 0 with a warning and records it under `[[patch.unused]]` in
  `Cargo.lock`. The applier's checks fail on that entry, on any resolution where `cargo metadata`
  doesn't show the crate at the target version from the vendored directory, and on a vendored
  directory that isn't exactly pristine + variant.
- **Capture:** `graft capture` diffs the copy cargo resolves (the vendored crate after
  `graft apply`, else the registry source, which every project on the machine shares) against
  the pristine `.crate`. A `target/` directory and cargo's `.cargo-ok` marker are not part of the
  package.

### 10.3 go

- **Versions** are written as the go command writes them (`v0.14.0`); a version given without
  the `v` (`--version 0.14.0`) is normalized.
- **Pristine:** `go mod download -json <module>@<version>`, run outside any module so the
  project's `go.mod` and `go.sum` are untouched: the module cache's extracted copy, verified
  against `go.sum` and the checksum database, and read-only. The environment's `GOPROXY`,
  `GOPRIVATE` and `GONOSUMDB` apply.
- **Versions:** `go list -m -versions` (retracted versions excluded).
- **Installed copy:** `go list -m -json <module>` in the main module (`ecosystems.go.module`,
  default the project root): its `Version`, and `Replace.Dir` (else `Dir`).
- **Install:** `go get <module>@<version>`; reinstall: `go mod download`. A project with
  `vendor/modules.txt` also gets `go mod vendor`.
- **Applier `go-replace` (the default and only one):** pristine + variant is written to
  `.grafts/.vendor/<module, / as +>-<version>/` (committed; it MUST have a `go.mod`), and a
  **version-qualified** `replace <module> <version> => ./<that directory>` is set with
  `go mod edit` in the main module's `go.mod`, or with `go work edit` in `go.work` when
  `go env GOWORK` names one. Other replaces of the module are dropped. Version-qualified, so after
  a bump the replace stops applying and the check fails, instead of applying an old variant to
  new code; for a new version, `sync` installs with `go get`, which moves the `require`.
- **Silent failure:** a replace for a version that isn't selected is ignored, and `go build`
  exits 0. The applier's checks fail unless `go list -m` shows the module at the target version
  from the vendored directory, on an unversioned or other-version replace of the module, on a
  `vendor/modules.txt` that doesn't record the replacement, and on a vendored directory that
  isn't exactly pristine + variant.
- **Capture:** `graft capture` diffs the module's replacement directory (the vendored module
  after `graft apply`, or any directory a `replace` points at) against the pristine module. When
  the module resolves to the module cache, which is read-only and pristine, capture is refused
  with `capture/read-only`, saying where to edit instead.

### 10.4 pypi

- **Names** compare normalized (PEP 503: `Typing_Extensions` is `typing-extensions`).
- **Versions** use PEP 440 (§4.1). In YAML, quote a version that would read as a number
  (`verified: "24.0"`); the scaffold does.
- **Pristine:** the published **wheel**, the artifact that gets installed: `pip download --no-deps
  --only-binary :all: <name>==<version>` (the project's interpreter's pip, else `python3`'s; the
  pip configuration and index apply), extracted. For packages that publish only platform wheels,
  `ecosystems.pypi.platform` picks the platform tag. A package with only an sdist can't be a
  `patch` graft (its source belongs in the `fork` mechanism).
- **Versions:** the index's JSON API (`ecosystems.pypi.index`, default `https://pypi.org/pypi`);
  yanked releases are skipped.
- **Installed copy:** the project's interpreter (`ecosystems.pypi.python`, else
  `.venv/bin/python`, else `python3`) reports the distribution's version and site-packages
  directory (`importlib.metadata`); wheel paths are relative to it.
- **Tool:** uv when `uv.lock` exists, poetry when `poetry.lock` exists, else pip.
- **Install:** uv: `uv lock --upgrade-package <name>==<version>` and `uv sync`; pip:
  `python -m pip install <name>==<version>`. Reinstall: uv: `uv lock --upgrade-package` for each
  vendored wheel, then `uv sync`; pip: `pip install -r` the requirements file, then
  `pip install --force-reinstall --no-deps` the vendored wheels.
- **Applier `wheel-vendor` (the default and only one):** pristine wheel + variant is repacked,
  with `RECORD` regenerated and the published wheel's filename and version (a `+local` label
  would be another version to resolvers), as `.grafts/.vendor/<wheel>` (committed). uv projects
  get `[tool.uv.sources] <name> = { path = ".grafts/.vendor/<wheel>" }` in `pyproject.toml`;
  uv applies sources to direct dependencies only, so a package that isn't in
  `[project] dependencies` is refused with a reason. pip projects get the package's line in
  `ecosystems.pypi.requirements` (default `requirements.txt`) replaced by the wheel's path
  (its trailing comment kept). Poetry projects are refused for now.
- **Silent failures:** pip treats a wheel of the same name and version as "already satisfied"
  even when its contents changed, and exits 0, so the installed copy stays unpatched or stale;
  uv refuses a changed wheel (hash mismatch) but keeps the old hash on a plain `uv lock`. The
  applier's checks fail on a vendored wheel that isn't pristine + variant, on a `uv.lock` that
  doesn't lock the package to the wheel or pins another build's hash, and on a requirements file
  that doesn't install the wheel; the installed-files check (§9.1) catches an installed copy
  that isn't pristine + variant whatever the tool did.
- **Capture:** `graft capture` diffs the distribution's files in site-packages against the
  pristine wheel: the wheel's own top-level packages and modules, walked in site-packages (so a
  file added or removed there is part of the change), never the rest of site-packages.
  `.dist-info` and `.data` (rewritten or relocated by installers), `__pycache__` and `.pyc` files
  are not compared. Installers may hardlink site-packages files from their cache (uv on Linux),
  so an edit there can reach the cache too; `graft apply` replaces the installed copy.
